## 一、一句话结论

这篇帖子把 DSH 团队提出的 **Super-agent 架构** 拆成五个模块（双层架构、事件驱动、多信道交互、计算/状态/环境分离、Watchdog），核心论点是：**Agent 系统的瓶颈已经从"模型能力"转移到"人的注意力"和"系统底座的调度能力"**，因此要从操作系统与编译器的老概念里借工具（fork、页换入换出、投机执行、控制回路），而不是继续在 prompts / tools / skills 层打补丁。

---

## 二、问题定义：为什么现有 Agent 架构不够用

帖子的推理链条很干净，四步：

1. **人类角色上移**：模型变强后，人从"底层执行"退到"顶层决策与验收"。
2. **Personal Agent 出现但没质变**：今年早期的 OpenClaw 一类工具演化为 Personal Agent，本质是"更好用、延迟更低"，架构上没有新东西。DSH 团队自身并未推出 dsh bot，社区 bot 都由社区开发。
3. **真正的硬约束是人的注意力**：现有 Agent 以**单个 Session** 为单位，Session 之间彼此独立、靠手动切换；作者与团队观察一致——**个人注意力上限约 3–5 个 Session**，再多就记不住、效果骤降。
4. **扩 Session 也不解决问题**：MCP 只解决扩展性，上下文混乱与单会话同步阻塞依然存在。

由此得到全文最锋利的一句判断：

> **单任务的上限取决于模型能力，多任务的上限取决于人的注意力。**

Super-agent 架构的目标因此被定义为：**打破单任务间的上下文边界，让 Agent 跨会话保持上下文，同时推动多项任务**——从用户侧彻底"淡化 Session"。

## 三、五个模块逐层拆解

### 3.1 双层架构：Router + Worker

解决的是**吞吐 vs 连续性**的矛盾：全塞进一个 Session → 连续但慢；开足够多 Session → 快但割裂。

| 层 | 角色 | 职责 | 模型要求 | 结构 |
|---|---|---|---|---|
| **Router** | 秘书/大总管 | 与人交互、跨任务信息汇总与决策、分发；**不执行具体任务** | 轻量模型即可，兼顾速度与效果 | 多节点，但只做分发，不管任务细节 |
| **Worker** | 干活的专家 | 独立上下文执行单一任务，挂载完整执行工具 | 能力最强的模型 | 多节点，复杂任务可 **fork subagent**，单个 Worker 自身可成为 Agent Teams |

关键是：**系统在底层接管上下文管理与并发**，用户侧只看见一个 Super-agent。作者在这里点名批评了一类开源 multi-agent 项目——"把用户当项目经理"是错误路线：

> **Session 不能成为用户负担。**

与 Agent Teams 的差别也点得很准：Team Lead 要管任务细节，Super-agent 的 Router 只管分发。

### 3.2 事件驱动：Trigger / Thread / 路径分流

- **Trigger（触发器）**：群聊消息、邮件与日程提醒、代码审查评论、CI 结果等环境事件。它把交互从**拉取式（prompt→响应）**改成**事件驱动**，Agent 可主动发现任务。
- **降噪两层**
  - **程序层（Fast Path）**：规则/程序过滤，绝大多噪声在这层就死了，根本不进模型。
  - **语义层（Slow Path）**：剩下的进 LLM，用提示词策略 + 上下文判断是否要行动。
- **路由直通优化**：为避免全局 Router 被打爆，过滤后的消息**直接路由给订阅它的 Worker**；Router 只保留两件事——**新任务冷启动** 与 **跨任务协调**。
- **Thread**：具备连续完整上下文的 request 集合（一个 PR、一封邮件往来、一个 IM 话题）。原文比喻精准：

  > **一条 Trigger 是一个点，一串相关的 Trigger 连成一条线，这条线就是 Thread。**

- **两条路**：Thread 无人认领 → Slow Path，Router 判定归属、建 Worker 并让它订阅；已有人订阅 → Fast Path，程序直接投递。一个 Worker 可同时订阅多条 Thread。

### 3.3 上下文注入：Inline / Spill 与链式召回

问题：注入多了挤占窗口、稀释注意力；注入少了模型反复调工具、增加轮次。**浪费上下文窗口是大忌。**

借编译优化思路：

- **Inline**：近期大概率要用的信息直接内联进窗口，省掉工具往返。
- **Spill**：超预算或低频的完整信息留在窗口外，窗口内只保留引用或摘要，按需读取。
- 作者比喻：**手边放常用的，剩下的放档案柜。**

作者最值得一读的独立判断就在这里——**和操作系统页换入换出的"同与不同"**：

- 相同：窗口就那么大，常用的换进来、不常用的换出去，窗口里维护一张页码对照表。
- 不同：**谁来换**。OS 缺页由硬件与内核自动处理，程序无感；LLM 没有这个机制，东西被 Spill 出去后，**模型得自己意识到"我这儿还有个引用"，再主动调工具读回来**。读不读、读多少全靠自己判断。

推论（也是本文最重要的工程暗示）：**这套机制对模型能力的要求反而更高，它必须知道自己缺什么**。同一套 Inline/Spill 换个模型效果能差很多——这解释了为什么"上下文管理"不是纯工程问题。

**链式召回（Chain of Recall）**：给 Trigger / Thread / Worker 都编 ID，注入时顺带带上"下一跳"的 ID，底层对象因此连成一张**引用图**。示例链路：群消息 → 挂着的 Thread ID → 正在处理它的 Worker → Worker 状态里挂的 PR Thread ID → 修改记录。

> 它靠的不是一个巨大的记忆库，而是一张**能实时渲染的地图**。

**投机执行（Speculative Execution）**：在结果是否被采用还不确定时，**用额外后台算力换人类等待时间**——按环境信号提前尝试，有价值就交付，没价值就丢弃。

### 3.4 多信道交互：异步 ReAct Loop

借计算机网络的全双工概念：用**异步 ReAct Loop** 消除后台耗时操作对前台对话的阻塞，会话无需等上一条命令跑完即可接受新指令。

- 传统 ReAct：`run()` 发出去整个循环卡住，再发消息只能排队 → 阻塞式一问一答。
- 异步：`start()` 立刻返回"已启动"，继续 loop，工具执行完再回传结果。

作者的横向核对（这点诚实，值得肯定）：ChatGPT 与 Claude Code 都已有类似能力，只是叫法不同——Claude Code 的 subagent 分前台/后台，后台可与主对话并行、跑完通知带回结果，前台仍阻塞主对话；ChatGPT 在长任务执行中可继续补充要求、修改约束。

**落地状态**：该异步机制**已在 DeepSeek Harness 中实现，但尚未默认开启**。

### 3.5 计算、状态与环境的分离

先定义三者：

- **计算** = Agent Loop 正在跑的过程
- **状态** = 会话记录、任务记录
- **环境** = 真正干活的代码仓库、本地文件、工具链

若三者同机：关机就停工、换机就丢环境。解耦分两步：

1. **计算与状态分离**：Agent Loop 放进云端可替换容器，会话状态独立入库。容器挂了换一个，状态在就能续跑。
2. **计算与环境分离**：**反过来做**——不把本地环境搬上云（未提交改动、私有凭据、特定硬件与工具链搬上去，结果大概率不一样且坑多），而是本地环境不动，端上装一个**轻量 daemon**，只负责执行命令、回传结果。

这就是 **BYOM（Bring Your Own Machine）**：个人电脑、甚至偶尔才上线的机器都能接入。

作者同时点出前提风险：**云端与端侧必须互信，云端一旦被攻破，它连着的所有设备都危险。**

### 3.6 Watchdog：外部控制回路

实现持久在线，除了存算分离还要能从异常恢复。要点：

- 长期可靠的分布式系统很难只靠主系统内部逻辑，需要**主系统之外**的独立外部控制回路（Control Loop）。
- 传统保活/心跳脚本不够用——**Agent 里常见故障不是进程丢了，而是 LLM 内部循环死锁或偏离执行目标**。
- 方案：配置 **Watchdog Session**，由**定时消息驱动**，及时介入、发现异常、纠偏、做故障恢复；它本身也是一个 Agent Session，开发者可以直接问它"为什么出错"并即时调整。

## 四、和既有方案的定位差异（作者的对比框架）

| 对比对象 | 它解决的问题 | Super-agent 的差异 |
|---|---|---|
| Claude Code（单 Agent + Main Loop + Skills + Tools/MCP） | **一项任务内部**的推理结构精简：可合并的 subagent 流程提炼成 Skills，需要留的 subagent 由主 Agent 工具调用 | 讨论的是**一组任务如何长期并行推进且让人少操心**；前者精简任务内结构，后者组织跨任务执行 |
| Agent Teams | Team Lead 管任务细节 | Router 只做分发，不管细节 |
| Personal Agent（社区 dsh bot 等） | 更好用、延迟更低 | 从底层接管上下文与并发，淡化 Session |
| yetone 的 `/loop` 三循环工作流（盯 GitHub 判断是否修、盯 X 有无反馈、盯代码要不要清） | 靠多个常驻 loop 覆盖固定关注面 | 用 Trigger+Thread+订阅把"盯"变成系统能力，而非人手写 loop。作者自嘲：此前用 /loop 迭代跑 72 小时，产出一坨 shit |

全文的价值主张浓缩成一句：

> **所有 Agent 架构绕来绕去，还是绕不开计算机底层的那些玩意**——Session 共享、缓存、CPU 的 fork 线程与子线程、Worktree、Filesystem。

以及结尾的立场：与其炒作 tools 和 skills（"再怎么优化拿到 Transformers 的注意力机制上也是抽卡"），不如优化底层，**这才是通往 AGI 的路子**。

## 五、独立评价

### 5.1 站得住的地方

1. **问题选得准**。把瓶颈从"模型不够强"改判为"人的注意力 + 系统调度"，这与一线重度使用者的体感高度吻合（3–5 个 Session 的上限几乎是通用经验值）。
2. **概念借用不是装饰**。Inline/Spill 对齐页换入换出、投机执行对齐 CPU 分支预测、Watchdog 对齐控制回路——每一处借用都带出了具体的工程差异（尤其"谁来换页"这一点，直接推出模型能力要求更高）。
3. **降噪分层与直通路由**是能立刻抄的设计：程序层先杀掉大部分噪声，语义层只处理残渣；Router 只做冷启动与跨任务协调，避免全局单点被打爆。
4. **"Session 不能成为用户负担"** 是全文最该被抄进产品设计文档的一句。

### 5.2 值得追问的地方

1. **Slow Path 的判定精度就是新单点**。Router 用轻量模型判"这条消息要不要行动"，误判成本不对称：漏判=任务永远不启动（人根本不知道），误判=烧算力。帖子没有给出评估口径（召回/精确率、人工兜底通道）。
2. **Spill 依赖模型"自知缺什么"**。这是把系统可靠性绑在模型的元认知上。工程上通常要补一层强制机制（预算水位告警、必读清单、召回失败自动重试），帖子未展开。
3. **投机执行的算力账**。后台提前跑，扔掉的概率多高？token 成本按倍数放大时，"用算力换等待"是否仍划算，缺少成本模型。
4. **Watchdog 自身的看门狗**。Watchdog 是 Session、也由模型驱动，它偏了谁纠？至少需要非模型的外部判据（进程/心跳/预算/输出不变式）。
5. **BYOM 的信任模型是最大安全面**。daemon 常驻个人电脑、云端可下发命令——这就是一条标准的远控通道。帖子只说"互信"，未提权限分级、命令白名单、审计、断连熔断。
6. **链式召回的可观测性**。引用图会随任务变长而变复杂，"实时渲染的地图"如何防止引用环、如何做失效清理，工程细节空白。

### 5.3 一句话总评

**这是近一年 agent 工程讨论里少见的"往下走"而非"往横铺"的文章**：不新增概念名词堆砌，而是把 Session、订阅、上下文预算、守护进程这些老问题重新用系统软件的坐标定位了一遍。它的价值不在于每个模块都新（异步 ReAct、后台 subagent、容器化 Agent Loop 都已有实践），而在于**把它们组织成一套能解释"人为什么累"的完整因果链**。真正待验证的是第二层：这些机制的**误判率、成本、以及失控时的兜底**，帖子一个都没量化。

## 六、可落地的借鉴清单

按"投入产出比"排序，个人/小团队可以直接借的：

1. **把注意力当资源做预算**：同时活跃任务强行限制在 3–5 条，超出就进队列而不是开新 Session。
2. **两级降噪**：先写死规则过滤（关键词/来源/是否 @我/是否待办），剩下的才让模型判。
3. **Thread 化**：所有输入先归到"一串相关事件"上，再决定谁处理；不要每条消息独立起一个会话。
4. **订阅式直通**：任务一旦有人（Worker）认领，后续消息直接投给它，不要每条都过总调度。
5. **Inline/Spill 显式化**：在提示里明确"当前窗口内有什么、档案柜里有什么、需要时用哪个工具取"，降低模型瞎找的概率。
6. **ID 链路**：给任务、线程、执行者编 ID，并在注入上下文时带上下一步的 ID，让"追问"能顺着图走。
7. **后台守护用独立会话**，而不是往主流程里塞心跳；让它能被人类直接质问。
8. **本地执行 daemon 只做最小权限**（命令白名单 + 审计日志 + 一键熔断），这是 BYOM 唯一的现实落地姿势。

## 九、附：与当前 DSH 环境的对照

本文写作时使用的正是 DeepSeek Harness 的运行时，可对照验证文中若干说法：

| 文中机制 | 当前环境中的对应物 |
|---|---|
| Worker 可 fork subagent | `subagent` / `subagent_fork`（子代理独立上下文，回传结果而非中间步骤） |
| 事件驱动的多节点编排 | `workflow`（脚本化 fan-out，phase/pipeline/parallel） |
| Router 的跨任务协调与冷启动 | `create_goal` / `update_goal`（跨轮次持续性目标） |
| 异步/非阻塞会话 | 后台 job（`run_in_background` + `job_output` / `job_kill`），前台不阻塞 |
| Watchdog 的纠偏会话 | 由 goal + 子代理状态巡检承担，尚无独立常驻看门狗 Session |
| 全双工"随时插话" | 帖子明确指出该异步 ReAct 机制**已实现但未默认开启**，与本环境行为一致 |

也就是说：**文中描述的不是纸面推演，其中大半能力在当前运行时里已经能摸到对应按钮**，缺的主要是 Router 层的全局自动化与 Watchdog 的独立常驻。
